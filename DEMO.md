# Local flight evidence demo

This demo runs in `holycow_git`, not the sibling publication copies. It adds a
separate real pipeline evidence workflow to Flight log; existing fictional
cattle, alerts, Spotlight, planning and browser-local recordings are unchanged.
No publishing or Supabase connection is needed.

## Prepare once

Use Python 3.11+ and Node 22.13+. Run from `holycow_git` in PowerShell:

```powershell
python -m venv ml/.venv
ml/.venv/Scripts/python.exe -m pip install -r ml/requirements.txt
npm --prefix web ci
ml/.venv/Scripts/python.exe ml/prepare_demo.py 'C:/path/to/13277315-uhd_3840_2160_25fps.mp4'
```

The exact original clip is [Pexels: Drone View of Cows Walking in a Field](https://www.pexels.com/video/drone-view-of-cows-walking-in-a-field-13277315/).
Keep its stock-footage license with any redistributed media. This is demo stock
footage, not a HolyCow-captured ranch flight. `prepare_demo.py` verifies the
source SHA-256 against the bundled predictions, then makes a silent 1280×720
H.264 playback copy with fast-start metadata. It does **not** run inference.
Local media is ignored by Git. This workspace's copy is already prepared.

`ml/demo-assets/prepared.json` contains compact, actual per-frame xyxy boxes and
video track IDs from `ml/outputs/cows-verified.jsonl`, generated by
`cow_segment.py` with bundled scene weights, stride 1, threshold 0.55. Source and
prediction SHA-256 hashes are retained in its provenance. All 818 frames are
retained; polygons and uncalibrated vote scores are omitted from this box viewer.
The original coordinates are 3840×2160 at 25 fps (32.72 seconds).

To regenerate prepared boxes **only after running the actual pipeline**, use:

```powershell
ml/.venv/Scripts/python.exe ml/prepare_demo.py 'C:/path/to/13277315-uhd_3840_2160_25fps.mp4' --predictions ml/outputs/cows-verified.jsonl --metadata ml/outputs/cows-verified.metadata.json
```

Do not point this at arbitrary footage: the color model is specific to this
scene. Inference verifies the original source hash too. Other flights require
new reviewed annotations, retraining and independent evaluation.

## Start two local processes

Terminal 1, from `holycow_git`:

```powershell
$env:HOLYCOW_DEMO_SOURCE = 'C:/path/to/13277315-uhd_3840_2160_25fps.mp4'
ml/.venv/Scripts/python.exe ml/demo_service.py --port 8765
```

Prepared-results mode only needs the Python standard library, bundled JSON and
prepared playback MP4. It works even if the ML dependencies, weights or original
source are unavailable. `HOLYCOW_DEMO_SOURCE` is only needed for inference.
This workspace can use `../.cow-vision-venv/Scripts/python.exe` instead of the
new virtual environment and the source currently in the user's Downloads folder.

Terminal 2, from `holycow_git/web`:

```powershell
npm run build
npm start -- --port 8790 --var HOLYCOW_DEMO_SERVICE_URL:http://127.0.0.1:8765
```

Open [the local app](http://127.0.0.1:8790). Stop the Worker before rebuilding.
The documented Windows development-runtime issue still applies; use this built
Worker path. Nothing is published.

`HOLYCOW_DEMO_SERVICE_URL` is a **server-side Worker binding**, never a public
frontend variable. For development, put that binding in local Wrangler vars;
the command above supplies it without editing generated config. The Python
service binds only to `127.0.0.1`, rejects browser Origin headers and provides no
CORS. Every browser API/video request goes through `/api/demo-flight/*` in the
existing web control layer. Do not expose this local service to the internet.
There is no production authentication or multi-tenant isolation in this demo.

Optional `HOLYCOW_DEMO_STATE` changes the service-owned state directory; default:
`ml/demo-state/`. Keep it the same across restarts. It holds SQLite, per-job
outputs and local diagnostic logs. No source filesystem paths are returned by
the HTTP API. No credentials are needed.

## Job and review behavior

- `POST /api/demo-flight/jobs` accepts the fixed `scene-flight` asset, mode
  `inference` or `precomputed`, and a 32-character lowercase UUID hex request ID.
  It immediately returns a queued job. A background thread executes the Python
  pipeline as a subprocess **inside the Python service**, never in a Worker.
- `GET /api/demo-flight/jobs` restores job summaries and reviews after refresh;
  `GET /api/demo-flight/jobs/:id` returns the evidence and append-only history.
  State is queued → running → completed/failed. Inference progress comes from
  the pipeline's actual processed/total frame output. Unknown progress is
  indeterminate. Prepared mode says no inference and only loads saved results.
- At most one job runs at a time. SQLite stores idempotency keys; repeated starts
  with the same key return the original job. Additional starts while active
  return that active job. Restart marks interrupted jobs failed with an explicit
  explanation; jobs are not silently rerun. Start again to retry.
- `GET /api/demo-flight/assets/scene-video` streams only a known playback asset
  with byte-range support for seeking. Arbitrary file paths are never accepted.
- `POST /api/demo-flight/jobs/:id/reviews` validates a known detection, action
  flag/resolve/reject, nonempty note ≤2,000 characters and expected history
  sequence. A stale save gets 409; the viewer reloads history and preserves the
  unsaved note. Resolve/reject requires an open flag; decided observations may
  be flagged again. Actor is the explicit local “Demo reviewer”.
- `POST /api/demo-flight/reset` clears only demo job and review rows, including
  idempotency keys. It refuses while a job is active. It never deletes source
  footage, models, prepared results, existing fictional dashboard fixtures or
  browser-local recordings. Generated per-job diagnostic files remain on disk.

The control layer allowlists operations and IDs, rejects foreign mutation
origins, checks JSON and body size, streams media and reports service outages
without replacing them with fictional data. The Python service validates all
review/business commands and owns durable SQLite transactions.

## Repeatable three-minute walkthrough

1. **0:00–0:30:** Open Flight log → Process demo flight. Show the fixed scene clip
   and the warning that arbitrary footage is unsupported. Select **Precomputed
   results (no inference)** → Load precomputed results. Explain these are actual
   saved pipeline outputs, not live processing. Use this path for a time-bounded
   presentation; full CPU inference may take over three minutes.
2. **0:30–1:15:** Inspect detections. Play/scrub the video and watch the boxes
   follow frames. Use “Jump to first track sighting” to select a later track:
   selection pauses and seeks to the recorded timestamp. Boxes use the source
   coordinate SVG viewBox over the full uncropped video; Fullscreen evidence
   keeps both the video and overlay. Video track IDs never identify registry cows.
3. **1:15–2:00:** Select a detection, add “Review possible boundary overlap”,
   and Flag for review. Add a second note and Resolve flag (or Reject flag).
   Show the ordered saved history. These are observations, not health diagnoses.
4. **2:00–2:40:** Close, refresh, reopen Flight log and inspect the saved job.
   Select its flagged-observation entry: the viewer seeks to the saved evidence
   and shows both notes. Restart the Python service if desired; the same SQLite
   history remains. Show duration, processing status, 131 geometric tracks in
   the prepared output, and open/historical flag counts. Explain fragmentation
   makes track totals unsuitable as a cattle census.
5. **2:40–3:00:** Close evidence and use Reset demo jobs and reviews for the next
   run. Source/model/prepared assets remain. Separately demonstrate the inference
   option when time allows: watch actual frame progress and inspect the new job.

## Checks

```powershell
python -m unittest discover -s ml -p test_demo_service.py
cd web
npm run typecheck
npm run build
# Start the service and built Worker first; wait for any inference to finish.
$env:TEST_ORIGIN = 'http://127.0.0.1:8790'
npm run test:control
npm run test:demo
```

Backend tests use temporary SQLite and cover transitions, duplicate starts,
failure, unavailable inference with prepared fallback, invalid IDs/payloads,
conflicting reviews, resolve/reject, restart durability, reset protection,
known-media access and byte ranges. The intentional failure tests print local
tracebacks. Web demo integration tests create one prepared test job and two
review events; reset those through the demo reset after testing if desired.

## Limits

Local, trusted-machine hackathon software: no production authentication,
multi-process job scheduler, cancellation, automatic retries, streaming upload,
cross-flight identity matching, clinical inference or measured model accuracy.
Run one service process per SQLite state directory. Scene-color segmentation can
miss, merge or split cattle, producing 131 distinct tracks over this clip while
only 23–29 predictions are present in individual frames. These are unverified
model observations. Saved prepared output was produced on the training scene,
so it is not independent validation. Media is local and must be prepared on a
fresh checkout; a hosted Worker cannot access your computer's loopback address.
