# Ingestion, authorization and operations

For the deployed Supabase development project, use [the provider-specific operations and access contract](../supabase/README.md). It preserves a separate backend/control layer, uses verified user context through `cattle_backend_user`, and denies direct browser cattle access. Standalone deployment groups below are not the active Supabase roles.

## Flight-to-alert walkthrough

1. Authenticate the uploader through the chosen auth provider. A trusted backend verifies issuer/subject and organization membership; an ingestion credential is scoped to one organization and allowed drone/flight. Create/find `flight` by `(org_id,source_key)`. Add cow-ID-based `clip` manifests with 30 fps, duration, expected count, parsed identifier and optional candidate animal UUID. A filename/parser result is not an accepted identity.
2. Allocate immutable object keys under a tenant prefix, with no overwrite permission. Upload images to private staging storage; do not open a SQL transaction while transferring bytes. Compare checksum, size, content type, dimensions, image index and manifest. Only the backend marks `media_asset.state='ready'` after successful object verification. Database and object store are not atomically committed: reconcile pending rows/orphan objects with a durable job, quarantine mismatches and retry incomplete uploads. A clip is complete only when expected image indices/count and checksums pass; don't run a whole-clip score on a partial clip unless the policy explicitly permits it.
3. For each stored image create `frame` at offset zero, with actual capture instant and clock quality. Images reference their own objects, rather than treating milliseconds of a missing video as evidence. Preserve actual fps/timing; 30 fps offsets have sub-millisecond fractions. Optional source videos use one video asset and multiple bounded offsets. Ground position is supplied animal data with CRS/method/uncertainty; drone telemetry has separate position and altitude datum in payload.
4. Create/find a queued `inference_run` by tenant request key, frozen model/version/digest, complete config, processing version and explicit input frames. An exact request must match the existing immutable request/config/input scope. Create input rows and output batches transactionally. Detection-producing runs create detections and temporary tracks; metric models may reference these through `output_input` and emit measurements without duplicating detections. Whole-clip outputs use a representative input frame plus window bounds and clip ID in schema-versioned payload; `run_input` lists all actual frame inputs. Missing/unassessable scores have a finding output, not a zero numeric value.
5. Transition queued → running → succeeded or failed. Output and publication row locks serialize competing writers. Source inputs/outputs are frozen at terminal status. Use short chunk transactions while running; partial rows are diagnostic only. A single final transaction verifies expected output manifest/counts, taxonomy/schema, finite values, all declared inputs, lineage, object readiness, tracking completeness and adapter invariants, then marks succeeded. The DB checks ready inputs, state transitions, immutable config and terminal publication; **output count completeness and JSON schemas require the adapter**. Never treat status alone as proof of model accuracy.
6. A resolver reads only succeeded, policy-selected runs. Write accepted/unresolved identity decision and evidence in one transaction. A parsed RFID claim needs the reader/time/track alignment or human review needed by the confirmed policy. Anonymous detections/tracks remain valid. Add resolved locations, with NULL ground position when not assessable. `location_observation` enforces completed source/track runs and same-flight provenance. Other resolved finding/survey inputs must be validated by the resolver for scope, completed source runs and evidence completeness before writing; these semantic checks are not all DB triggers.
7. Translate gait/estrus scores into findings only using approved scale-specific versioned thresholds. Preserve conflicting predictions, record the selected outputs or fusion policy, and never average arbitrary model confidence. Findings can remain suspected, negative, or not assessable. Human acceptance of a finding does not establish a veterinary diagnosis. A rule creates an alert with an idempotency key and append-only lifecycle events. Review rejection immediately invalidates its effective visibility; its original alert/history remain.
8. The synthetic fixture demonstrates initial wrong identity → corrected RFID association, late older location, anonymous animal, two disagreeing gait versions, survey staleness and reviewer-rejected suspicion. Re-read current views after a correction, append an audit event with affected IDs and before/after summaries, invalidate any identity-dependent rule conclusions, and supersede affected surveys. No materialized location cache needs refreshing.

## Retry, concurrency and visibility contract

Source keys are stable within their uniqueness scopes: flight per tenant; clip/asset per flight; image index per clip; frame offset per asset; output per run; track key per run. Object keys are unique per tenant, never signed URLs. Inference request keys distinguish an exact transport retry from an intentional new processing attempt. Retrying a failed attempt creates a **new request key/run UUID** with `retry_of`; different model/config/pipeline processing also gets a new run. Every attempt keeps its partial results for debugging until retention permits removal.

For an exact retry, begin a transaction, look up scoped key, compare canonical immutable content (including object hash/size and payload/config/input set). Return the existing ID on an exact match; reject a reused key with changed content (HTTP 409 or equivalent). If absent, `INSERT ... ON CONFLICT DO NOTHING RETURNING id`, then in a **new READ COMMITTED statement** select and compare the winner's row. A concurrent uncommitted winner blocks the insert; if it aborts the insert can succeed. Do not use last-writer-wins upsert on evidence. A one-statement CTE lookup may miss the concurrent winner's snapshot. At SERIALIZABLE, retry the entire transaction on serialization failure.

Terminal runs reject new output inserts even if a duplicate key would later conflict; the retry adapter therefore returns an existing matching output before attempting insertion into a published run. For a complete-run replay, validate the manifest and return the published run, rather than replaying inserts. A mismatch is never silently deduplicated. The SQL fixture demonstrates uniqueness mechanics, not a production HTTP adapter.

Output batches are visible to worker/diagnostic queries while running. Application-facing resolved state is written only after successful publication; current map/finding/survey queries must not aggregate raw running outputs. Transactionally write each resolved finding and its evidence, each survey and its source run list, and each decision/review/alert event plus supporting audit data. A failed resolver transaction must not leave half an interpretation. The trusted service enforces those boundaries; there is no pretense of an implemented queue lease/outbox.

Concurrent corrections use a known head UUID and unique successor. Reject/reload on `23505` or zero affected rows. Preserve user intent by asking for review when the head changed rather than silently selecting the new head. Publication and structural output inserts lock the same inference run row. Append-only tables cannot be updated/deleted by ordinary code. Deliberate retention is an administrative workflow.

## Authorization model

Runtime DB roles are NOLOGIN groups, NOBYPASSRLS and not owners. The migration owner is separate. Grant one or more groups to trusted backend LOGIN roles according to service scope:

| Product actor | DB group | Scope |
|---|---|---|
| Viewer | cattle_reader | Tenant-scoped reads, including authorized evidence metadata |
| Operator | cattle_operator | Manage ranch/herd/cattle, identifiers, effective membership/boundaries |
| Reviewer | cattle_reviewer | Append identity/location interpretations, findings/reviews, surveys, in-app alerts/events |
| Ingestion worker | cattle_worker | Upload/flight/telemetry/model/run/output writes; terminal status updates; no identity approval |
| Owner/admin | cattle_admin plus necessary operator/reviewer groups | Manage membership and versioned alert policy; no arbitrary evidence deletion |

Membership has owner/admin/operator/reviewer/viewer product roles. Operators who review need the reviewer group too. Initial organization/owner onboarding is a controlled administrator/service procedure; no self-service tenant creation function or auth provider is invented. No runtime TRUNCATE, DELETE evidence, UPDATE history, schema DDL, or broad superuser privileges are granted. Reviewer actor strings and worker metadata are trusted-backend assertions, not authorization proof.

For each pooled request: authenticate; derive authorized tenant and product role; `BEGIN`; `SET LOCAL ROLE <fixed allowlisted group>`; parameterized `SELECT set_config('app.org_id',$1,true)` and `app.actor`; execute parameterized queries; `COMMIT` or `ROLLBACK` on all paths before releasing the connection. SET ROLE identifiers cannot be arbitrary user strings. Never set tenant context at session scope in a reusable pool. Membership authorization must come from a trusted auth claim/mapping service; looking up a caller-supplied tenant with unrestricted credentials is not sufficient.

RLS uses a custom tenant GUC. **Any holder of backend database credentials can set that GUC**. This design assumes a trusted backend and prevents missed application filters, not hostile SQL clients who can choose their tenant. Do not expose these roles directly through a browser SQL API. A provider with direct JWT database access needs a policy tied to its verified claims instead. Parameter binding does not make exposed credentials safe.

All tables have RLS/FORCE RLS; views use invoker security (PostgreSQL 15+ feature, baseline 16). Missing tenant context produces no rows. Composite FKs enforce tenant relationships independently of RLS. Superusers and BYPASSRLS always bypass policies; FORCE RLS does not restrain them. Table owners can alter policies/triggers. A deployment gate must rerun the role tests using the **actual deployed LOGIN**, confirm its group memberships/ownership/BYPASSRLS flags, and test pooled tenant switches and error cleanup. Proposed group-role tests alone cannot certify an as-yet nonexistent deployed auth integration.

Keep media private with encryption, tenant-prefixed keys and backend storage policies. Evidence endpoint must authenticate and check the frame/output's tenant before issuing a short-lived download URL; recheck storage state and audit access as required. Never authorize by object key supplied by the browser alone. Retention-purged media returns unavailable without losing the evidence tombstone. No credentials, signed tokens, faces beyond required evidence, or reader secrets belong in metadata/audit payloads. Storage lifecycle is as important as row access.

## Safe migration and recovery

The ordered SQL files each run in a transaction with no automatic rerun. Use a migration ledger in the deployment runner recording filename, SHA256, applied time and operator; never edit an applied migration. The first release targets an empty schema, so regular index creation is appropriate. For a populated system later: expand/backfill/validate/contract; nullable additions first, batched updates, NOT VALID FK/check validation where appropriate, separately scheduled exclusion/index changes, and `CREATE INDEX CONCURRENTLY` outside a transaction when needed. Set reviewed lock/statement timeouts and observe blockers. Rehearse changes on a restored staging copy and test the auth roles before routing traffic.

Preflight server/PostGIS compatibility (`SELECT version(); SELECT PostGIS_Full_Version();` after extension installation), provider extension support, available cluster role names, encoding/timezone, space for indexes/WAL and backup restore. No extension or provider provisioning has been executed in this task. Raw SQL is intentional; if a future ORM is introduced, preserve these constraints/policies and configure spatial mapping explicitly.

Failed statements within one migration roll back that file; a successfully applied previous migration remains. A later functional problem should get a new forward repair migration. Dropping a schema/extension or applying a reverse migration after writes can destroy history; it is not an automatically safe rollback. Stop writes and restore a verified backup/PITR point into a separate database if forward repair cannot protect integrity, then reconcile post-restore inputs before switching traffic.

## Retention, backups and recovery targets to confirm

Proposed planning defaults only: media 30 days, raw predictions/telemetry 90 days, resolved observations/reviews/audits one year; retain selected supporting clinical/review evidence longer only under an explicit contract. Identifier/membership/boundary/model metadata must remain as long as dependent history needs them. Confirm contractual, animal-management and privacy requirements before enabling deletion. Evidence legal/review holds override ordinary expiry.

Retention is a privileged, audited job, not runtime `DELETE CASCADE`. All foreign keys default to NO ACTION. Retire cattle rather than deleting them. For media expiry: verify no hold, write audit manifest, mark purged and enqueue object deletion; retry deletion/reconcile storage inventories and keep hash/key/timestamp tombstones. Do not mark an available object ready after purging without a controlled restoration. Blob deletion and DB state change need reconciliation; they are not atomic. Source evidence linked to retained findings must either remain under hold or explicitly show as expired.

For structured-data expiry, archive required lineage/evidence first, enumerate dependency graph, remove/supersede affected derived state, then child link/alert/review/observation records before model/source rows, by tenant and bounded time window. Validate counts/checksums and record a deletion audit manifest. Append-only triggers must be deliberately disabled only by an offline maintenance owner in a controlled transaction for specifically approved tables, then reenabled before commit. Prefer retaining skinny lineage/tombstones; arbitrary partition drops are not a valid shortcut. Audit events about deletion are retained separately through the approved policy.

Proposed targets, not service guarantees: RPO ≤15 minutes for database writes using continuous WAL/PITR, RTO ≤4 hours for an initial small deployment. Object storage versioning/replication and backup policy must be measured separately. Daily encrypted backups plus WAL/PITR retention (initially 7–14 days), off-host copy, restricted restore credentials and checksum monitoring. Store role/grant bootstrap definitions and extension versions with backup metadata; schema dumps alone omit cluster roles.

Monthly and before major migrations, restore to a separate disposable environment: provision matching extensions; restore role ownership/grants/schema/data and a selected PITR timestamp; run integrity/query/RLS checks with real application roles; verify sampled object keys, hashes and decryptability; reconcile pending jobs; measure restore duration and actual recovery point; document gaps and securely dispose of restored credentials/data. Database restores do not restore deleted image objects. Keep media backup/retention aligned with required evidence recovery. No backup/restore drill or latency benchmark ran during this design task.
